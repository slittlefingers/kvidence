# KVidence 实验报告：中深层 KV 反演与观测引导搜索

实验日期：2026-10-16；资料与成本分析补充：2026-10-17（Australia/Melbourne）  
报告范围：本地合成数据实验，以及第 12 节的公开 Pixel 10 性能记录与条件性成本估算。本文汇总原始指标，未为撰写报告重新训练或重新运行模型；第 12 节不是新增设备攻击实验。

## 摘要

本系列实验考察两个相关问题：一是能否通过训练一个反演器，从中深层 KV 直接恢复 token；二是在没有离线反演器的情况下，能否用约 200 个候选的实测 KV 学习一个代理映射，指导后续候选搜索，降低对语言概率先验的依赖。

在 TinyStories 小模型、126 个已知 token 类别上，训练式反演器在第 4、8 层的 384 条未见过的 16-token 序列上均实现完整恢复。在单 token 搜索实验中，候选数从 2,048 扩大到 10,000 后，固定 200 次初始查询仍能形成有效排序。进一步换成 Qwen2.5-0.5B，将 embedding table 从 50,257 × 64 扩大到 151,936 × 896 后，在 10,000 候选的均匀目标组中，第 24 层代理在累计 220 次查询时恢复 28/32 个目标，600 次时恢复 32/32；同期随机搜索为 0/32、2/32，语言概率排序均为 0/32。

后续 Gemma 4 E2B IT 实验使用真实 8-bit affine 权重，并配对比较原生 BF16 KV 与运行时 KV8。10,000 候选的均匀目标组中，第 15 层两种 KV 模式在累计 220 次时均恢复 32/32；该缓存也被第 35 层复用。

这些结果支持“中深层 KV 包含可学习的 token 信息”和“少量实测 KV 可以提供搜索方向”这两个有限范围内的假设。MLX 运行时 KV8 在所测条件下未消除这种信息。当前证据不包含全词表、未知前缀、多 token 联合恢复、真实无空格长密码或手机 NPU 量化 KV。对按语言概率采样的目标，概率排序在小预算下通常仍有优势。

## 1. 研究问题与术语

研究动机是：如果目标是随机字符、秘密片段或其他低语言概率内容，单靠自然语言概率排序可能把正确候选排在很后面。是否可以利用已观测的目标 KV，以及候选 embedding 与深层 KV 之间的对应关系，建立一个由观测驱动的搜索框架？

本文区分三个不同的规模：

| 术语 | 本文含义 |
|---|---|
| 模型词表 / embedding table 行数 | 原预训练模型保存的 token embedding 行数，实验不删改这张表 |
| embedding 维度 | 每个 token 的连续向量维度，如 64 或 896 |
| 候选数 | 一次恢复任务实际允许搜索的 token 子集大小，如 126、2,048、10,000 |

token ID 是离散标签，不能直接对 ID 大小求有意义的梯度；已知 embedding 则提供连续坐标。本次“方向”具体指代理预测的 KV 距离所产生的候选排序，不是 token ID 数轴上的方向。

本系列没有使用首层目标 KV。训练式反演使用 MLP 的反向传播；后续搜索使用闭式岭回归，尚未实现对未知输入 embedding 的梯度下降、soft-token 优化或多 token 联合优化。原语言模型在所有实验中均冻结。

## 3. E1：训练式 KV 反演

### 3.1 方法与数据划分

从冻结语言模型的真实 `past_key_values` 中提取同一位置的 K 和 V，拼接为 128 维 FP32 特征。第 4 层和第 8 层各训练一个独立反演器：`128 → 256 → 256 → 126`，每个 131,198 参数。只有反演器参与 AdamW 与交叉熵训练，原语言模型不更新。

输入类别为 64 个英文词、26 个小写字母、26 个大写字母、10 个数字。每个类别前有空格，并验证其在原 tokenizer 下恰为一个 token。序列包括英文词/数字混合、随机字母数字以及纯数字；这是受控的空格分隔输入，不是真实密码字符串。

| 集合 | 序列数 | 每条长度 | 内容 |
|---|---:|---:|---|
| 训练 | 2,048 | 16 | 混合、随机字母数字各一半 |
| 验证 | 256 | 16 | 与训练同类，完整序列互斥 |
| 测试 | 384 | 16 | 混合、字母数字、纯数字各 128 条 |
| 长度外推 | 96 | 32 | 三类各 32 条 |

seed 为 `20261016`。四个集合的完整输入序列互斥，但 token 类别共享；没有测试未见过的类别。归一化统计只来自训练集，训练 50 epochs，仅按验证准确率选 checkpoint，第 4、8 层分别选择 epoch 3、10。

反演器逐位置接收 KV，不接收正确前缀、目标 token ID、embedding 或语言模型 logits；与后续需要正确前缀的搜索实验不同。独立 [invert.py](kv_inverse_tiny/invert.py) 可只加载保存的 KV、反演器与 tokenizer 解码，不加载原语言模型权重或真实标签。

### 3.2 准确率与负对照

| 层 | 16-token 测试 token 准确率 | 16-token 整串恢复 | 32-token 外推 token 准确率 | 32-token 整串恢复 |
|---|---|---|---|---|
| 4 | 100.0000% | 384/384 | 99.9674% | 95/96 |
| 8 | 100.0000% | 384/384 | 100.0000% | 96/96 |

16-token 测试中每层共 6,144 个 token，三类输入各自均完整恢复。32-token 外推中，第 4 层仅在一条纯数字序列上出现一个错误；第 8 层无错误。

| 对照 | token 准确率 | 整串恢复 |
|---|---|---|
| 最常见类别基线 | 4.8014% | 0/384 |
| 第 4 层，打乱 KV | 2.2624% | 0/384 |
| 第 8 层，打乱 KV | 2.2949% | 0/384 |

打乱 KV 与真实标签的对应关系后，准确率大幅下降，支持反演器利用了 KV 中与 token 对应的信息。它不构成对所有数据泄漏可能性的形式证明，也不证明能恢复候选集外 token。

### 3.3 在线延迟：与自实现全候选匹配比较

12 条 held-out 的 16-token 序列，三类各 4 条，两种方法在两层均恢复 12/12 条完整序列。全候选基线逐位置计算 126 个候选的真实 KV，复用已经预测的前缀 cache，只运行到观察层；不输入正确前缀标签。

| 层 | 全候选匹配 / 每序列 | 已训练 MLP / 每序列 | 延迟比 |
|---|---|---|---|
| 4 | 18.518 ms | 0.049 ms | 378.1× |
| 8 | 34.104 ms | 0.048 ms | 703.5× |

这是 warm 状态下每条 16-token 序列的延迟中位数。MLP 计时包含归一化、前向、argmax；排除下载、加载、磁盘读取、离线训练和生成目标 KV。模型 KV 提取约 0.77 秒，两层反演器训练各约 2.6 秒，需另计并通过多次使用摊销。

**378× / 703× 仅针对这个 126 类、自实现全候选基线，不是对论文 Collision+ 的加速倍数。** 它也不能移用到后续 10,000 候选在线拟合搜索实验。

原始证据：[指标](kv_inverse_tiny/results/metrics.json)、[延迟数据](kv_inverse_tiny/results/benchmark.json)、[详细说明](kv_inverse_tiny/README.md)。

## 4. E2–E5：观测引导搜索的共同方法

### 4.1 威胁模型与计数

目标是一个未知 token，位于已知、正确的英文前缀之后。攻击者可访问原模型权重及 embedding，知道 KV 层、位置与布局。E2–E4 获得完整 FP32 K+V；E5 改为读取实际 BF16 或 KV8 缓存及量化元数据，细节见第 8 节。8 个固定前缀涵盖故事、颜色、数字与秘密代码等简短场景；不是未知整段输入恢复。

每个任务先随机选择 200 个不同候选，实际执行模型前向得到 KV。四种方法共享这 200 个候选及观测，初始选择不使用目标 ID。随后按每批 20 个候选继续查询，累计预算为 `200、220、240、300、400、600`。达到预算前不因命中而停止，每种方法最多查询 600 个互不重复的候选。

目标 KV 的生成模拟已经泄漏的观测，不计入攻击查询；共同前缀预处理、概率 logits 计算、加载与下载不计入该候选查询数。生成模拟目标时使用真实 ID，但候选选择函数只接收目标 KV，不接收真实 ID。最终答案由已查询候选的真实 KV 距离最小值决定。

### 4.2 四种方法

| 方法 | 后续候选选择规则 |
|---|---|
| 随机 | 从未查询候选中随机选择 |
| 语言概率 | 完整原模型在正确前缀下的下一 token 概率从高到低排序 |
| KV 代理 | 用已查询 embedding/KV 对拟合映射，预测未查询候选的 KV，按与目标 KV 的距离排序 |
| 打乱 embedding 对照 | 使用同样代理，但固定打乱 token 与 embedding 的对应关系 |

KV 代理先按已观测样本统计标准化 embedding 和 KV，拟合带截距的岭回归：

```text
minimize ||X W + 1 b - Y||²_F + (0.01 × n) ||W||²_F

X、Y：仅来自已查询候选的标准化 embedding / KV
n：当前已查询样本数
b：不正则化的截距
```

每批前向后，把新增观测并入训练点并重新拟合；不加载 E1 的反演器。预测还原到原始 KV 尺度后排序，已查询候选排除。评分扫描所有候选 embedding，但不提前计算全部候选的真实 KV。

真实距离记录为 `mean((KV_candidate - KV_target)²) / mean(KV_target²)`，分母按脚本设下界。对于固定目标，该归一化不改变候选的真实距离排序。恢复数指最终真实距离选中的精确 token ID，不是相近语义或预测距离下降。

Qwen 的 embedding 为 896 维，而观测点为 200–580，代码使用与原问题等价的对偶 ridge 解，降低求解矩阵大小；截距仍不正则化。独立数值检查中，原始解与对偶解的前 100 个排序一致。这里欠定的是未正则化映射估计，不代表正则化问题不可求解。

### 4.3 两种目标分布与样本数

`uniform_target` 从候选集均匀采样，用于削弱语言先验的优势；它不是无空格随机密码经 tokenizer 后的真实分布。`model_probability_target` 按原模型在前缀下的候选条件概率采样；它也不等于真实自然语言语料。

| 实验 | 首轮 seed / 每分布每层目标数 | 复核 seed / 每分布每层目标数 | 本文主表口径 |
|---|---|---|---|
| E2：2,048 候选 | 20261017 / 16 | 20261018 / 32 | 独立复核，n=32 |
| E3：10,000 候选 | 20261017 / 16 | 20261018 / 32 | 独立复核，n=32 |
| E4：Qwen，10,000 候选 | 20261017 / 16 | 20261018 / 16 | 两轮合并，n=32 |
| E5：Gemma 4，两种 KV 模式各自统计 | 20261017 / 16 | 20261018 / 16 | 每模式两轮合并，n=32 |

同一目标分别观察两个层，不能把两个层算成独立目标以增加统计量。E2、E3 各有 192 个“目标 × 层”案例，E4 有 128 个；E5 每模式有 128 个，共 256 个配对“模式 × 目标 × 层”案例。pilot 均不纳入正式汇总。

## 7. E4：更大模型与 embedding table

换成 Qwen2.5-0.5B base，观察第 12、24 层；每 token 的真实 K+V 为 256 维，即 2 个 KV heads × 64 head_dim × K/V。没有把 KV 复制为 14 个 query heads。观察第 12 层时前向只运行前 12 层，概率排序始终使用完整 24 层。

Qwen 的完整 embedding table 为 151,936 × 896，候选仍是 10,000。共有 41,393 个符合筛选条件的英文/数字 token；Qwen 会将 `" 1"` 切为两个 token，所以数字候选使用 `"1"` 等独立数字 token。候选要求单 token 编解码往返一致；试跑种子的全部 10,000 候选与 8 个前缀已逐一验证拼接编码边界，正式脚本也对每个目标断言。

原检查点为 BF16，运行时转成 FP32。下面是两个正式随机种子合并后的精确恢复数，每分布每层 n=32。

## 8. E5：Gemma 4 W8 与运行时 KV8 配对验证

### 8.1 实际量化对象

使用固定版本的 Gemma 4 E2B IT MLX 8-bit affine 权重，group_size=64；量化模块在前向中保留打包权重，不把完整模型反量化为浮点模型。部分归一化参数和激活仍是浮点。“8 位”不是“所有计算均为 signed INT8”。

原生缓存实测为 BF16，不能由“权重已量化”推断 KV 也为 INT8。本次增加配对的运行时 KV8 组：K/V 生成后立即保存成 8-bit affine 整数码、BF16 scale/bias；注意力使用这份打包缓存，误差会传递到后续层。不是事后对已有 FP32 KV 取整。分析时按完整量化元数据反量化，采用 MLX 默认 BF16 输出后再转 FP32 做拟合与距离计算。

本实验是 Apple MLX GPU 上的真实量化缓存 API 实验，不是手机 NPU，也不是物理内存 dump。手机现有 LiteRT Gemma 4 文件采用混合位宽，不能当作本次同一 W8 格式。

### 8.2 共享 KV 与搜索设置

Gemma 4 E2B 有 35 层，只有前 15 层生成独立 KV；后 20 层复用第 14 层的 sliding KV 或第 15 层的 full KV。最后第 35 层使用第 15 层的缓存，因此本次观察第 10、15 层的实际 full-attention KV，每位置宽度均为 1,024，没有虚构独立的第 35 层新 KV。

主 embedding table 为 262,144 × 1,536。模型还有 262,144 × 8,960 的额外 per-layer embedding，原模型前向使用它，但本次代理只用主 embedding。不同模型之间的差异不能单独归因于量化或维度。

两种 KV 模式均使用同一 W8 权重、10,000 候选、相同目标/前缀/初始 200 个索引和最高 600 次预算。每个模式、每种分布、每层为两个种子各 16 个目标，合计 32。概率目标统一按 native-KV 参考概率采样，保证配对；各模式概率基线使用本模式完整 35 层的 logits。前缀补 BOS，未使用聊天模板。

适配复用 MLX 的量化 cache/SDPA，为共享层提供不复制缓存的量化视图。所有独立 KV 生产层都量化。sliding 层在全部长度小于 512 的条件下使用非环形量化缓存与局部 mask；没有验证窗口淘汰后的行为。代码与适用范围见 [E5 README](kv_guided_search_gemma4_int8/README.md)。

### 8.3 精确恢复结果

下表为两个种子合并结果，每项分母 32，220 包含最初 200 次随机观测。

| 分布 | KV 生产层 | BF16 KV @220 | KV8 @220 | BF16 KV @600 | KV8 @600 |
|---|---|---|---|---|---|
| 均匀 | 10 | 16/32 | 16/32 | 31/32 | 30/32 |
| 均匀 | 15 | 32/32 | 32/32 | 32/32 | 32/32 |
| 模型概率 | 10 | 15/32 | 16/32 | 29/32 | 30/32 |
| 模型概率 | 15 | 26/32 | 26/32 | 28/32 | 29/32 |

均匀目标第 15 层，两种模式的初始 200 次均未命中，但再查询 20 个候选后均恢复 32/32；此时随机和概率排序均为 0/32。到 600 次，两种模式的随机为 2/32、概率为 1/32。

概率目标在 220 次时，概率排序两组均为 31/32，高于 KV 代理；600 次时概率排序均为 32/32。代理并非全面优于概率搜索。

配对分析中，均匀第 10 层 @600 有 30 个两组均成功、1 个仅 BF16 成功、1 个两组均失败；概率第 15 层 @600 有 27 个均成功、1 个仅 BF16 成功、2 个仅 KV8 成功、2 个均失败。量化路径会改变排序轨迹，少量成功/失败交换不足以证明稳定优劣。

四轮正式数据共 256 个“模式 × 目标 × 层”案例，全部完成轨迹审计和配对检查；所有方法与预算点中，未出现“目标已查询但最近 KV 选错”的情况。BF16 和量化计算不保证逐位一致，额外四探针数值核验中的 cached/full normalized MSE 约为 1.34e-4–3.71e-4，但最近邻均识别正确，原前缀缓存未改变。

结论是：**在所测条件下，8 位权重和运行时 KV8 仍保留足够的 token 搜索信息；量化不能被直接视为清除泄漏信息。** 这不是完整词表、未知前缀、真实密码或 NPU 场景的保证。没有未量化 Gemma 4 权重对照，因此本实验只隔离同一 W8 模型中启用 KV8 路径的影响，不能测量 W8 权重本身相对于原模型的损失。

完整四方法预算曲线和配对表：[E5 RESULTS.md](kv_guided_search_gemma4_int8/RESULTS.md)；[合并指标](kv_guided_search_gemma4_int8/combined_metrics.json)；[读取核验](kv_guided_search_gemma4_int8/oracle_validation.json)。

## 10. 验证、成本与证据边界

### 10.1 已完成验证

搜索轨迹检查覆盖候选映射唯一性、共享初始观测、预算内不重复查询、距离有限且非负、命中目标后真实距离选择正确 ID。Qwen 的审计还逐项重算汇总恢复数。正式数据在报告整理时再次通过检查。

Qwen [oracle_validation.json](kv_guided_search_large/oracle_validation.json) 中，第 12、24 层的缓存查询与完整输入前向、批量与单独查询的归一化差异均为 0，并确认原前缀 cache 长度未变。这是所测前缀和 token 的数值核验，不是所有输入上的形式证明。

报告中的结果表直接读取保存的 `metrics.json` 生成；主表不混入 pilot，也不将 MLP、在线 ridge 与全候选匹配的结果合并成同一种算法。

### 10.2 运行成本应如何理解

| 项目 | 首轮 / 第一项 | 复核 / 第二项 | 执行情况 |
|---|---|---|---|
| E1：KV 提取 | 0.768 秒 | — | CPU |
| E1：反演器训练 | 第 4 层 2.624 秒 | 第 8 层 2.642 秒 | CPU；两个不同层模型 |
| E2 | 7.082 秒 | 14.311 秒 | 分别执行 |
| E3 | 9.713 秒 | 18.865 秒 | 两轮并行 |
| E4 | 211.250 秒 | 207.135 秒 | 两轮并行 |
| E5 seed 20261017 | BF16 KV 86.598 秒 | KV8 89.100 秒 | 四轮串行，单个模型实例 |
| E5 seed 20261018 | BF16 KV 87.182 秒 | KV8 87.624 秒 | 四轮串行，单个模型实例 |

E1–E3 使用 macOS ARM64、CPU 4 threads；E4 用 Apple MPS 执行 FP32 模型前向，CPU 4 threads 拟合和排序。E3 两轮并行执行，E4 两轮也并行执行，其墙钟时间受资源竞争影响。E5 使用 MLX GPU 量化前向与候选打分、CPU 4 threads 求解 ridge，四轮串行。上述搜索时长是整批实验运行时间，不是单目标攻击延迟，后端变化也不能被解释为单独的量化加速。

KV 代理每轮仍需给全部候选 embedding 打分，因此候选越多，拟合/排序开销仍会增加。可节省的是完整原模型候选前向，不是消除所有随词表增长的工作量。当前没有与论文 Collision+ 的原实现、同模型、同数据、同硬件进行端到端对照。

### 10.3 当前可以与不可以得出的结论

| 判断 | 当前证据 |
|---|---|
| 中深层 KV 存在可学习的 token 信息 | E1 在 126 类受控序列上支持，打乱 KV 对照显著退化 |
| 少量实测 KV 能帮助排列未知候选 | E2–E5 的均匀目标支持，打乱 embedding 对照未达到相同效果 |
| 不必依赖自然语言概率才能恢复候选 | 在本次均匀 token 分布和正确前缀条件下支持 |
| 扩大模型后方向搜索立即失效 | E4 不支持该判断；固定 200 次初始观测仍有帮助 |
| 8 位 KV 自动消除可恢复的 token 信息 | E5 不支持该判断；所测均匀组第 15 层仍在 220 次恢复 32/32 |
| 代理始终优于语言概率 | 不支持，概率目标的小预算结果多次相反 |
| 能恢复全词表、真实长密码、未知整段输入 | 尚未测试 |
| 已实现并验证基于输入梯度的攻击 | 尚未实现；当前在线代理为 ridge |
| 对 Collision+ 有确定加速倍数 | 没有同条件原实现比较，不能声称 |
| 已验证真实内存取证端到端攻击 | 没有；当前 KV 通过本地模型 API 获得 |

本报告与此前 Android / LiteRT-LM 内存清理及地址读取实验不同。这里不包含物理 dump 搜索、地址定位、已释放内存读取、KV 布局自动识别、数据恢复率或清理开关的评估。训练式反演和搜索方向实验只验证“已经获得对应 KV 后”的恢复环节。

## 11. 下一阶段建议（尚未执行）

1. **扩大候选覆盖。** 在同一模型上逐步扩展到全部有效英文/数字 token，再覆盖完整可用词表；尽量固定目标和初始观测做配对比较。
2. **改用真实字符串。** 随机生成无空格字母数字密码、不同长度和格式，交给真实 tokenizer 切分；区分单 token 恢复与整串成功率。
3. **去掉正确前缀假设。** 用已预测前缀继续恢复，测量错误传播和 KV 位置偏移，并加入 beam 或多假设搜索对照。
4. **测量 200 点的适用范围。** 扫描初始预算、embedding 维度和上下文长度；分析代理误差、有效秩、真目标排序与失败案例。
5. **加入真实部署条件。** 已验证 MLX KV8，下一步覆盖更低位宽、噪声、量化元数据缺失、窗口淘汰及实际 NPU KV 格式，再连接内存取证入口。
6. **公平比较搜索策略。** 加入从第一次查询就按概率排序的基线、同条件 Collision+、embedding 距离基线以及代理的探索/混合策略；统一报告前向次数与端到端时长。
7. **单独验证梯度方案。** 若采用连续 embedding 优化，必须评估投影回真实 token 的误差与成本，并与当前 ridge 排序保持同预算对照。

|---|---:|---|

| Prefill | 91 token/s | 处理输入序列的速度 |
| TTFT | 0.30 秒 | 首个输出 token 的等待时间 |

该项目使用 LiteRT-LM `v0.14.0-alpha.0`；测试说明中的 EdgeTPU southbound 为 `0.14`，`edgetpu_performance_mode` 关闭。这是开发者的第一手设备记录，不是 Google 官方性能保证，也不是我们的 v0.18.0 修改版实测。来源未完整披露这组测速的上下文长度、重复次数等条件，不能据此确认 10,000 或 100,000 token 时的吞吐。

同一来源中较高的 prefill 数字 386–605 token/s 对应输出已损坏的自定义量化模型，不能作为正确运行的官方 Gemma 4 E2B 模型性能引用。[原始 README](https://raw.githubusercontent.com/bejoyfuuul/litert-lm-tensor-g5-npu/main/README.md)

### 12.2 逐位置全词表扫描需要多少次前向

定义待恢复长度为 \(N\)，每个位置的可用候选数为 \(V\)。取 \(V=262{,}144\) 作为 Gemma 4 embedding table 全行数的扫描预算；实际有效 token 集应排除不可用或不允许的特殊 ID，预算随实际候选数线性变化。

计算假设为：已有各目标位置对应的 KV；模型、布局、位置编码及量化信息已知；从前到后恢复，每次都能正确识别当前 token，并复用已经正确恢复的前缀状态；每个位置完整测试全部 \(V\) 个候选。此时：

\[
Q_{\mathrm{full}}=\sum_{i=1}^{N}V=NV.
\]

| 待恢复上下文长度 \(N\) | 全扫描候选前向次数 \(NV\) |
|---:|---:|
| 10,000 token | 2,621,440,000（约 26.2 亿） |
| 100,000 token | 26,214,400,000（约 262.1 亿） |

这是指定扫描策略的查询预算，不是所有攻击必需的下界。若目标在搜索顺序中均匀分布、匹配可可靠判定且一旦命中便停止，平均每位置约需 \((V+1)/2\) 次查询，总量约减半。语言概率排序、剪枝、Collision+ 或本报告的代理排序会改变查询数；不能把完整扫描预算当作论文 Collision+ 的实际成本。

若只恢复正确已知前缀之后的一个未知 token，全扫描预算约为 \(V\)，不是 \(NV\)。反之，若无法逐位置可靠匹配并继续使用正确前缀，\(NV\) 模型也不足以描述多假设搜索、错误传播或回溯成本。它没有枚举所有 \(V^N\) 条完整序列。

### 12.3 条件性时间估算

令 \(R(i)\) 为前缀长度约为 \(i-1\) 时，完整候选测试循环的有效吞吐，单位为候选/秒。它应包含候选前向、前缀状态恢复或分叉、KV 读取与距离比较等成本。则：

\[
T_{\mathrm{full}}\approx T_{\mathrm{setup}}+\sum_{i=1}^{N}\frac{V}{R(i)}.
\]

仅在把吞吐简化为常数 \(R\)、不计准备开销时，才有 \(T\approx NV/R\)。下表按一天 86,400 秒、一年 365.25 天计算：

| 假设候选吞吐 \(R\) | 恢复 10,000 token | 恢复 100,000 token |
|---:|---:|---:|
| 14.7 候选/秒 | 约 5.65 年 | 约 56.51 年 |
| 100 候选/秒 | 约 303.41 天 | 约 8.31 年 |
| 1,000 候选/秒 | 约 30.34 天 | 约 303.41 天 |
| 10,000 候选/秒 | 约 3.03 天 | 约 30.34 天 |

**表中所有候选吞吐均为计算假设。14.7 这一行只是借用公开 decode 数字作量级演示，尚未测得 14.7 候选/秒，更不能据此声称 Pixel 10 攻击需要 5.65 年。** 对话中取整为 15 候选/秒得到的“约 5.5 年”，与此处精确使用 14.7 得到的 5.65 年属于同一种条件性估算。

连续 decode 会把生成的 token 依次追加到同一前缀；collision 测试则需要让多个候选从同一前缀出发，并读取目标层 KV。两者状态管理不同。Prefill 的 91 token/s 也不是 91 个独立候选/秒：一条输入序列里的后续 token 会依赖前面的 token。当前 [NPU executor 的 Prefill](../../LiteRT-LM/runtime/executor/llm_litert_npu_compiled_model_executor.cc) 明确检查 batch size 为 1，不能把 prefill 的序列长度直接解释为独立候选批量大小。候选并行能否实现以及能加速多少，需要单独验证。

### 12.4 上下文长度影响与当前部署边界

在完整注意力层中，位置越靠后，需要访问的前缀 KV 越多，因此单次候选计算的注意力部分通常随前缀长度增加；不能默认短前缀测速可在整个长上下文中保持不变。滑动窗口层自身的注意力访问受窗口大小约束，但模型还包含完整注意力层，所以不能据此假定整个模型的候选测试耗时恒定。实际增长还取决于编译图、缓存布局、内存带宽和设备运行状态。

当前 Ghost APK 的 [bridge.c](../../annoymous/app/src/main/cpp/bridge.c) 对 Gemma 4 设置 `max_num_tokens=4096`。**现有应用配置没有验证 10,000 或 100,000 token 的运行，更没有完成这些长度的 NPU 恢复实验。** 上述数字是容量支持、KV 可取得且可正确匹配等条件均满足时的成本模型，不能作为现有 APK 的能力声明。

### 12.5 对 KVidence 方法的启示

全词表逐位置扫描的候选量随 \(NV\) 增长；在移动设备上，减少昂贵的原模型候选前向具有明确的研究价值。本报告的代理方法尝试用约 200 次实测建立 embedding → KV 的排序，再追加少量真实查询。E5 的 10,000 **候选**实验中，第 15 层均匀目标在 220 次累计查询时恢复 32/32，但这不等于已恢复 10,000 **上下文 token**，也不能直接外推到 262,144 候选或未知长前缀。

下一步需要在同模型、同目标、同观察层和同设备上测量：不同前缀长度下的实际候选/秒；前向、KV 读取及状态恢复各自的耗时；代理拟合与全候选打分开销；全词表查询数和逐位置恢复的错误传播。单观察层截断前向也可能与公开完整模型 decode 耗时不同。只有这些条件得到验证后，才可以给出相对于全扫描或 Collision+ 的端到端加速倍数，以及恢复长上下文的可信时间估计。
